# 受領フォルダ 分類 → OCR → ファイル一覧 自動更新(AgentCore / Google Drive版)

Google Drive上の受領フォルダに溜まっていくファイルを、まず「支払(領収書・請求書)」
「売上」「給与」「銀行通帳」の4種類に分類する。支払に分類されたものだけ内容を読み取り
(OCR)、リネームしたコピーをDrive上の`整理済`フォルダ配下の、受領フォルダと同じサブフォルダへ保存する
(従来の処理と同じ)。売上・給与に分類されたものは、OCRは行わず、
「最終取引日(YYYYMMDD)_元ファイル名.拡張子」にリネームして`整理済`フォルダ配下の、受領フォルダと同じサブフォルダへ
コピー保存する。銀行通帳は「最終取引日(YYYYMMDD)_銀行名.拡張子」にリネームして
`整理済`フォルダ配下の、受領フォルダと同じサブフォルダへコピー保存する。**4種類すべてについて**、処理結果を
`filelist.xlsx`に1行追記し、受領フォルダの元ファイルは削除せずそのまま残す
(コピーと元ファイルの両方が残ることになるが、`filelist.xlsx`への記録により
再実行時は処理済みとしてスキップされるため、重複コピーは発生しない)。
仕訳データ(弥生会計形式)の作成は別スキル`receipt-to-journal`が担当する
(対象は支払のみ)ので、このスキルでは行わない。何度でも再実行できるように、
`filelist.xlsx`に記録済みのファイルは前回までに処理済みとみなして自動でスキップする。

このスキルは、判断を伴う処理(Step 2〜3の分類・OCR読み取り)はClaudeが`Read`ツールで
直接行い、判断を伴わない機械的なDrive操作(Step 1の新規ファイル検出・ダウンロード、
Step 6のアップロード・旧ファイルのtrash)は専用スクリプト
(`scripts/drive_sync_download.py` / `scripts/drive_sync_upload.py`)がGoogle Drive
APIを直接(かつファイル単位の処理は並列に)呼び出して行う。この2つのStepでは
`search_files`/`download_file_content`/`create_file`/`trash_file`をファイルの数だけ
逐次呼び出すことはしない(処理速度と、毎回のLLM判断に左右されない再現性のため)。
ローカルの一時作業ディレクトリ(`/tmp`)を使う点、Step 3/4の既存Pythonスクリプト
(`scripts/append_filelist.py`・`scripts/rename_and_save.py`)を無改造のまま使う点は
従来通り。

## MCPツール名について(実行環境による違い)

本文中の `mcp__task-manager__...` はAgentCore環境でのツール名。Claude Codeの
claude.aiコネクタ経由など、別の実行環境では同じtaskmanager MCPサーバーが異なる
プレフィックス(例: `mcp__claude_ai_taskmanager-mcp__...`)で登録されていることがある。

`mcp__task-manager__...` という名前のツールが見つからない場合、それだけで
「このツールは利用できない」と判断してその処理(履歴登録など)をスキップしては
いけない。必ず以下の順で確認すること。

1. まず本文記載のツール名でそのまま呼び出せるか試す。
2. 見つからない場合、ツール検索の仕組み(例: `ToolSearch`)があれば、
   `"taskmanager list_history create_history_entry update_history_entry list_frames list_clients"`
   のようなキーワードで検索し、この環境での実際のツール名を特定してから呼び出す。
3. それでも該当するツールが見つからない場合に限り、ユーザーにその旨を報告する。

**Google Driveの個別ファイル操作について**: Step 1(新規ファイル検出・ダウンロード)と
Step 6(アップロード・旧ファイルのtrash)は、下記の通り`scripts/drive_sync_download.py`・
`scripts/drive_sync_upload.py`がGoogle Drive APIを直接呼び出して行うため、
`mcp__google-drive__search_files`等をファイル単位で個別に呼び出す必要はない
(フォルダの検索・作成、同名ファイルの新規アップロード後の旧ファイルtrashも、
すべて各スクリプト内で完結する)。

## 対応する関与先(案件)とDriveフォルダID

関与先コードと受領フォルダIDの対応表は、このファイルに直書きせず、taskmanagerの
案件マスタ(DynamoDB `TaskClients`テーブル)を、MCPツール `mcp__task-manager__list_clients`
から都度取得する(taskmanagerのWebアプリ・AgentsPanel.jsxも同じテーブルを参照しており、
マスタは1か所で管理している。旧`receipt-agent-clients`テーブル/APIは廃止済み)。

`mcp__task-manager__list_clients` を引数なしで呼び出す。

レスポンス例:

```json
[
  {"clientCode": "11", "clientName": "AMORPHOUS事務所", "receiptFolderId": "1lSUy...", "renamedFolderId": null, "lookupBucket": "CLIENT"},
  {"clientCode": "12", "clientName": "Ikkoh株式会社", "receiptFolderId": "1w6R9...", "renamedFolderId": "1L-j-...", "lookupBucket": "CLIENT"},
  {"clientCode": "13", "clientName": "JAKALULU株式会社", "receiptFolderId": "1weJd...", "renamedFolderId": null, "lookupBucket": "CLIENT"},
  {"clientCode": "14", "clientName": "Maximo事業所", "receiptFolderId": "1QZ67...", "renamedFolderId": null, "lookupBucket": "CLIENT"}
]
```

指定された関与先コードがこのレスポンスに無い場合、または `receiptFolderId` が
未設定(キー自体が無い)の場合は、ユーザーにDrive上の受領フォルダのURL
(`https://drive.google.com/drive/folders/{フォルダID}`)を確認してから進める。

いずれの関与先でも、フォルダ構成は共通:

- 受領フォルダ(上記APIで取得した`receiptFolderId`)の直下(または再帰的な
  サブフォルダ)に、支払(領収書・請求書)・売上・給与・銀行通帳のファイルが
  区別なく溜まっていく(分類前の受け皿フォルダ)。**処理後もファイルはここから
  動かさない**(削除もしない。分類の別なく、整理済フォルダへコピーした後も元ファイルは
  常にこのフォルダに残る)。
- ファイル一覧: クライアントフォルダ直下(受領フォルダと並列)の `filelist.xlsx`(支払・売上・給与・銀行通帳の
  4種類すべてを記録し、「分類」列で区別する)
- 支払: リネームしたコピーを整理済フォルダへ保存する。保存先は受領フォルダの親フォルダ
  直下の `整理済` フォルダ(Driveの`parentId`をたどって取得する。ローカル版の
  「関与先フォルダ」に相当)配下に、**受領フォルダと同じサブフォルダ構成**で保存する
  (例: 受領 `旧/a.jpg` → 整理済 `旧/20260204_取引先_5800円_旅費交通費.jpg`。サブフォルダが無ければ作成する。
  `支払`・勘定科目名のサブフォルダは作らない。勘定科目名はファイル名に含まれる)
- 売上・給与: `<最終取引日YYYYMMDD>_<元ファイル名(拡張子除く)>.<拡張子>` にリネームし、
  受領フォルダと同じサブフォルダ構成で`整理済`フォルダ配下へコピー保存する
- 銀行通帳: `<最終取引日YYYYMMDD>_<銀行名>.<拡張子>` にリネームし、受領フォルダと同じ
  サブフォルダ構成で`整理済`フォルダ配下へコピー保存する
- いずれの分類も、整理済フォルダへのコピー後も受領フォルダの元ファイルは削除しない
  (受領フォルダ・整理済フォルダの両方に同じファイルが1つずつ存在する状態になる)
- 勘定科目名の参照元(参考情報。関与先によらず共通、支払のみで使用): `master/TKCマスタ.xlsx`
  の「勘定科目コード表」シート(Drive上のパスは別途確認)

## 全体の流れ

### Step 0. 対象関与先の決定とローカル作業ディレクトリの準備

`mcp__task-manager__list_clients` を呼び、関与先コード一覧を取得する。対象とする
関与先は、**ユーザーに確認を求めず**、以下のルールで自動的に決定する
(定期実行(スケジュール)など、応答を待つ相手がいない経路で呼ばれることを
前提とするため)。

- プロンプトに関与先コード(または関与先名)が含まれる場合: その関与先だけを対象にする。
- 含まれない場合: `receiptFolderId` が設定されている関与先すべてを対象にする
  (`receiptFolderId` が未設定の関与先は対象外)。

対象が複数ある場合は、関与先ごとに以下のStep 1〜7を順に最後まで実行し、1件終えてから
次の関与先へ進む(処理の途中でユーザーに確認や進捗確認を挟まない)。関与先ごとに、
以下を用意する。

```bash
mkdir -p /tmp/{案件コード}/receipt /tmp/{案件コード}/renamed
```

以降のStep 1〜7すべてで、この `/tmp/{案件コード}/` を「ローカル版での受領フォルダ」
として扱う。

### Step 1. Drive上の新規ファイルの検出とダウンロード

`scripts/drive_sync_download.py` を実行する。受領フォルダ配下の再帰列挙、既存
`filelist.xlsx`のダウンロード、「受領ファイル名」列との突き合わせによる新規
ファイル判定、新規ファイルのダウンロード(フォルダ階層を保ったまま
`/tmp/{案件コード}/receipt/`配下へ、複数ファイルは並列)までを1回の実行で行う
(この時点では支払・売上・給与・銀行通帳の区別なく、受領フォルダ配下の全ファイルが
対象になる)。

```bash
python scripts/drive_sync_download.py {案件コード}
```

受領フォルダ内のファイル名に「のコピー」が含まれる場合(例: `79976.jpg のコピー`)は、
スクリプトが列挙直後にDrive上で正しい名前(`79976.jpg`)へリネームしてから新規判定・
ダウンロードを行う。変換後と同名のファイルが同じフォルダに既にある場合はリネームせず
スキップする(stderrに`[rename_copy] skip`が出る)。これらの内容は`new_files`の該当要素の
`remarks`に入る。Step 4で`entries.json`を作る際は、この`remarks`をそのまま各エントリへ
引き継ぐこと(`filelist.xlsx`の`remarks`列に記録される)。

標準出力にJSON(`{"client_code", "receipt_folder_id", "old_filelist_file_id",
"new_files": [...]}`)が返る。`new_files`の各要素は旧来の`scan_new_receipts.py`と
同じ`filename`/`modified_at`(Drive上の更新日、JST)/`size_mb`/`type`に加え、Drive上の`file_id`を持つ
(`filename`はDrive上のフォルダ階層を`/`区切りで表した相対パスで、
`/tmp/{案件コード}/receipt/`からの相対パスと一致する)。同じ内容は
`/tmp/{案件コード}/new_files.json`にも保存され、`old_filelist_file_id`は
Step 6でのtrash対象として使われる。

`receiptFolderId`が案件マスタに無い等でスクリプトが解決できない場合は
`--receipt-folder-id {フォルダID}` を明示的に渡す。

新規ファイルが0件なら「新しいファイルはありません」と伝えて終了する
(ダウンロード済みの一時ファイルは削除してよい)。

**1回の実行で処理する件数の上限(コンテキスト超過対策)**: 画像・PDFを`Read`すると
その内容がすべて会話のコンテキストに積み上がり、件数が多いと
`API Error: 400 Input is too long` で実行全体が失敗する。これを防ぐため、
`drive_sync_download.py`が**1回の実行で返す`new_files`は最大5件**(`--limit`、既定5)。
5件を超える分はスクリプトがダウンロードせず、件数を標準出力JSONの`remaining`
(全新規数は`total_new`)として返す。`new_files`は全件をStep 2以降の対象とすること
(自分で件数を絞らない)。残りはファイル一覧に追記されないため、次回実行時に新規として
再び検出される。呼び出し側(ジョブLambda)が`remaining`が0になるまで自動で再実行する。
Step 7の報告の**最終行**に、機械可読の `REMAINING: <N>` を必ず書くこと
(`N`は`remaining`の値。0でも書く。複数の関与先を処理した場合は`remaining`の合計)。

また、`Read`する前に次のサイズ対策を行う(Step 2・3共通)。

- 画像(`.jpg`/`.jpeg`/`.png`等)は、Bash + Pillowで長辺2000pxに縮小し、JPEG(quality 80)で
  `/tmp/{案件コード}/resized/`へ保存したものを`Read`する(元ファイルはコピー保存用に
  そのまま残す)。
- PDFは`Read`の`pages`パラメータで読むページを絞る(原則1〜3ページ。領収書・請求書は
  先頭ページに主要情報があることがほとんど)。ページ数が多い通帳PDFなどは、最終取引日の
  確認のため先頭と末尾のページだけを読む。
- 同じファイルを`Read`し直さない。読み取った結果はすぐ`entries.json`に書き出す。

### Step 2. 分類(支払 / 売上 / 給与 / 銀行通帳)

Step 1で新規と判定した各ファイルを `Read` ツールで開き(画像なら画像として、PDFなら
PDFとして、Excel/CSVファイル(`.xlsx`/`.xls`/`.csv`。売上集計表や賃金台帳、銀行の
入出金明細はスキャン画像ではなくこの形式で受領フォルダに置かれることが多い)なら
表データとして)、内容から次の4種類のいずれかに分類する。

- **支払**: 領収書・請求書。関与先(自社)が代金を支払う側になっている書類
  (店舗のレシート、仕入先・外注先からの請求書など)。
- **売上**: 売上明細・売上集計表・POSレジ日計表や、関与先(自社)が代金を受け取る側と
  なっている請求書(自社が顧客に発行した請求書の控えなど)。
- **給与**: 給与明細書・賃金台帳・タイムカード集計など、従業員への給与支払いに関する資料。
- **銀行通帳**: 通帳の見開きページの写し・入出金明細・ネットバンキングの取引明細
  スクリーンショットなど。

**判断に迷う場合の注意点**: 「請求書」という書式だけでは支払・売上のどちらかは
決まらない。誰が誰に対して代金を請求しているか(発行元が関与先自身か、関与先の
取引先か)を必ず確認し、関与先が支払う側なら支払、関与先が受け取る側(自社の
売上)なら売上と判断すること。どの種類にも当てはまらない、または判断がつかない
場合は支払として扱う(従来通り Step 3〜5 の勘定科目名判定で判断がつかなければ
ファイル名の科目名部分が「未分類」になるため、後から人の目で見つけやすい)。

分類結果は `{"filename": "...", "classification": "支払"}` のような形でまとめておき、
以降のStepで参照する(ファイルへの保存形式は自由でよい。例えば Step 3 で作る
`entries.json` に支払分だけをまとめる、売上・給与・銀行通帳分は別途ファイル名の
リストとして保持する、など)。`classification` の値は `append_filelist.py` の
entries.jsonにそのまま渡す値と同じ表記(`支払`/`売上`/`給与`/`銀行通帳`)にすること。

### Step 3. 内容の読み取り(支払は全項目、売上・給与・銀行通帳は対象月判定用の日付)

**支払**: Step 2 で **支払** に分類したファイルだけを対象に、内容を読み取る
(ローカル版と同じ)。画像・PDFはOCRとして、Excel/CSVファイル(`.xlsx`/`.xls`/`.csv`)
は表データとして読み取る(支払についても、請求明細等がスキャン画像ではなくExcel/CSV
形式で受領フォルダに置かれる場合があるため。対応拡張子はStep 1(`EXT_TYPE`)で分類の
別なく共通)。

`filename` に「サブフォルダ名/ファイル名」が入っている場合は、
`/tmp/{案件コード}/receipt/<filename>` を開くこと。読み取る項目はローカル版と同一。

- 日付(領収書/請求書に記載の日付。西暦に変換する)
- 金額(合計・請求金額)
- 取引先(発行元の会社名・店名・個人名)
- 内容(何の費用か)
- 区分(「領収書」か「請求書」か)
- 支払方法(現金・カード・振込など。記載が無ければ「不明」)
- 消費税額(明記されていればその金額。無ければ null)
- 勘定科目名(参考情報。master/TKCマスタ.xlsx と照合)

画像が斜め・一部隠れている場合は、Bash + Pillow で該当部分を切り出してから再度 `Read`。

**売上・給与・銀行通帳**: 取引先・金額など支払のような全項目のOCRは行わない。ただし、
履歴(TaskHistory)への対象月(後述の`frame_codes`)反映を正確に行うため、ファイルに
記載されている日付を読み取り、対象月(`YYYY年M月`)を判定する。Step 2で分類のために
既に内容を確認済みであれば、その際の情報を使ってよく、必ずしも再度`Read`し直す
必要はない。

- Excel/CSVファイル(売上明細表・売上集計表・賃金台帳・入出金明細など、複数の取引行を
  持つことが多い)の場合: **全ての行**の日付列を読み取り、含まれる年月をすべて洗い出す
  (重複は除く)。1つのファイルの中で複数の月にまたがる取引が混在する場合は、その
  すべての年月を対象月として記録する。
- 画像・PDFファイル(通帳見開きページの写し・給与明細書1枚など)の場合も同様に、
  写っている日付(通帳なら複数の入出金日、給与明細なら支給日など)から年月を洗い出す。
- 読み取った年月一覧を、そのファイルの `target_months`(例:
  `["2026年6月", "2026年7月"]`)として記録しておく(Step 4で`entries.json`の対応する
  エントリに追加のキーとして保持すればよい)。日付が全く読み取れなかった場合は空リスト
  `[]`とし、Step 7でその旨をユーザーに報告する(対象月不明のまま履歴には反映しない)。
- **売上・給与・銀行通帳(全分類共通)**: リネーム用に、ファイル内の**最終取引日**
  (最も新しい取引・支給の日付、`YYYY-MM-DD`)を `last_transaction_date` として読み取り、
  Step 4の`entries.json`エントリに追加のキーとして保持する(上記の対象月判定で洗い出した
  日付のうち最も新しいもの)。読み取れなかった場合は省略してよい(ファイル名に
  「日付不明」が入る)。
- **銀行通帳のみ**: 上記に加え、**銀行名**(例: `三井住友銀行`。支店名は含めない)を
  `bank_name` として読み取り、同じく`entries.json`エントリに保持する。読み取れなかった
  場合は省略してよい(ファイル名に「銀行名不明」が入る)。
  なお同じ最終取引日・銀行名(売上・給与は同じ最終取引日・元ファイル名)のファイルが
  複数あると同名になり、後のものが前のものを上書きするので、そのようなファイルが
  あればユーザーに報告すること。

### Step 4. ファイル一覧への追記(全分類・ローカルで実行)

Step 3 で読み取った **支払** 分は、これまで通り `date`/`amount`/`vendor` などを含む
完全な内容で `entries.json` にまとめる。各エントリに `classification: "支払"` を
明示すること。

**売上・給与・銀行通帳** 分は取引先・金額等の全項目OCRを行っていないため、
Step 1(`drive_sync_download.py`)の出力(`filename`/`modified_at`/`size_mb`/`type`)に
`classification`(`売上`/`給与`/`銀行通帳`のいずれか)と、Step 3で読み取った
`target_months`(対象月のリスト。例: `["2026年6月", "2026年7月"]`。1件も読み取れな
かった場合は`[]`)を付け加えたエントリにする(`date`/`amount`/`vendor` 等の内容系
フィールドは引き続き省略してよく、その場合は該当セルが空欄になる)。`target_months`は
`append_filelist.py`側では参照されず`filelist.xlsx`には出力されない
(「日付」列は単一の日付しか持てず複数月を1セルに表現できないため)が、
`entries.json`自体には残しておき、後述の「対象月(frame_codes)の反映」で参照する。

支払分と売上・給与・銀行通帳分は同じ `entries.json` にまとめて1回で追記してもよいし、
分けて2回実行してもよい(`append_filelist.py` は複数回呼んでも「No.」列の連番を
正しく引き継ぐ)。

```bash
python scripts/append_filelist.py "/tmp/{案件コード}/entries.json" "/tmp/{案件コード}/filelist.xlsx"
```

この時点では `/tmp` 上で完結しており、Driveにはまだ反映されていない。

### Step 5. 【支払のみ】ファイルのリネーム・コピー保存(ローカルで実行)

このStepは支払分だけを対象にする。`entries.json` に売上・給与・銀行通帳分も
混在させている場合、このスクリプト自体は `classification` を見て自動でフィルタは
しないので、渡すファイルは支払分のみに絞ること(支払分だけの
`entries_payment.json` を別途用意して渡す。ファイル名は固定でこの名前にすること。
Step 6の`drive_sync_upload.py`がデフォルトでこのファイル名を読みに行く)。

```bash
python scripts/rename_and_save.py "/tmp/{案件コード}/entries_payment.json" "/tmp/{案件コード}/receipt"
```

これにより `/tmp/{案件コード}/renamed/<ファイル名>` が作成される
(ローカル版と同じ命名規則)。

### Step 6. Driveへの反映(アップロード)

Step 2で4分類のいずれにも新規ファイルが1件も無かった場合はこのStep自体を省略する。
それ以外の場合、`scripts/drive_sync_upload.py` を実行する。

```bash
python scripts/drive_sync_upload.py {案件コード}
```

このスクリプト1回の実行で、以下をすべて行う(6-1〜6-3相当。デフォルトでは
`/tmp/{案件コード}/filelist.xlsx`・`/tmp/{案件コード}/renamed/`・
`/tmp/{案件コード}/entries.json`・`/tmp/{案件コード}/entries_payment.json`・
`/tmp/{案件コード}/new_files.json`を読む)。**filelist.xlsxのDriveへの反映は
必ず最後に行う**(実ファイルのコピーが確認できた後でなければ「処理済み」の記録を
残さないため。詳細は次段落)。

1. **整理済ファイルの反映(支払)**: `entries_payment.json`(無ければ`entries.json`の
   うちclassificationが`支払`または未指定のもの)をもとに、対応する`renamed/`配下の
   ファイルを`整理済`フォルダ配下の、受領フォルダと同じサブフォルダへアップロードする
   (同名ファイルが既に存在する場合は、新規アップロード後に旧ファイルをゴミ箱へ)。
   複数ファイルは並列に処理される。
2. **売上・給与・銀行通帳ファイルの反映**: `--entries-json`で指定したファイル
   (デフォルト`/tmp/{案件コード}/entries.json`)のうち`classification`が
   `売上`/`給与`/`銀行通帳`のエントリについて、`/tmp/{案件コード}/receipt/<filename>`
   をアップロードする。いずれも受領フォルダと同じサブフォルダ構成で`整理済`配下へ置く。売上・給与は
   `<last_transaction_date>_<元ファイル名(拡張子除く)>.<拡張子>`、銀行通帳は
   `<last_transaction_date>_<bank_name>.<拡張子>`にリネームする(OCRは行わない。同名ファイルが既にあれば新規
   アップロード後に旧ファイルをゴミ箱へ)。受領フォルダ内の元ファイルは削除・移動しない。
3. **filelist.xlsx の反映**: 1・2でアップロードに失敗したファイルがあれば、
   アップロード前にそれらの行をローカルの`filelist.xlsx`から取り除く
   (「受領ファイル名」列に記載が無い=未処理、という次回実行時の判定と合わせて、
   失敗した分が確実に再処理対象に戻るようにするため)。そのうえで新しい
   `filelist.xlsx`をアップロード → アップロード成功を確認してから、
   Step 1で取得した旧`filelist.xlsx`のfileId(`new_files.json`の
   `old_filelist_file_id`)をゴミ箱へ移動する(**必ずアップロード成功後に行う**。
   逆順にするとアップロード失敗時にデータが失われる。旧ファイルが無かった場合は
   この手順自体が発生しない)。ローカルに`filelist.xlsx`が無い場合はこの
   手順をスキップする。

個々のファイルのアップロードに失敗しても処理全体は止まらず、失敗したファイルは
スキップして最後にまとめて報告される(標準出力のJSONの`failures`)。上記の通り、
失敗したファイルの行は`filelist.xlsx`には反映されないため、次回の定期実行時に
新規ファイルとして自動的に再処理される(手動での再実行も可能)。`failures`が空でない
場合は、対象ファイルをユーザーへ報告すること。

`整理済`フォルダの位置(受領フォルダの親フォルダ直下)をスクリプトが解決できない
場合は `--organized-folder-id {フォルダID}` を明示的に渡す。

**後片付け**: `/tmp/{案件コード}/` 配下は一時作業ディレクトリなので、Step 6完了後に
削除してよい(次回実行時は Step 0 で作り直す)。

### Step 7. 報告

分類ごとの件数を報告する。報告の最終行は必ず `REMAINING: <N>` とする(Step 1参照)。

- **支払**: 処理した件数と、それぞれの「対象月 / 取引先 / 日付 / 金額 / 区分 /
  支払方法 / 保存先フォルダ」を簡潔に報告する。対象月はStep 3で読み取った日付
  (西暦)から `YYYY年M月` の形式で算出する(例: 日付が `2026-06-15` なら対象月は
  `2026年6月`)。仕訳データの作成はこのスキルでは行わないため、必要であれば続けて
  `receipt-to-journal` スキルを使うようユーザーに伝える。
- **売上・給与・銀行通帳**: それぞれの件数と、ファイル名・保存先フォルダ・対象月
  (Step 3で判定した`target_months`。複数月にまたがる場合はその全てを列挙する)を
  簡潔に報告する(受領フォルダの元ファイルも削除せず残っている旨を伝える)。
  `filelist.xlsx`へはファイル名などの機械的な情報のみ記録しており、内容の
  読み取り・仕訳化はこのスキルでは行わない。日付が1件も読み取れず対象月が判定できな
  かったファイルがあれば、その旨も併せて報告する。

**履歴(TaskHistory)への反映**

ユーザーへの報告にあわせて、処理した関与先の履歴を**分類(支払/売上/給与/銀行通帳)
ごとに別々の1行**として更新する(1関与先について最大4件、分類ごとに独立した履歴行
として管理する。Step 2でその分類に新規ファイルが1件もなかった分類は対象外とし、
今回新規ファイルが1件以上あった分類だけを処理する)。

新規ファイルが1件以上あった分類ごとに、以下を繰り返す。

1. `mcp__task-manager__list_series` を呼び、`taskGroup`(=分類/category)がその分類名
   (`支払`/`売上`/`給与`/`銀行通帳`のいずれか)で `seriesName`(=シリーズ名)が
   `"資料受領"` である項目の `seriesCode` を控える(=タスク名(series_code)に使う値)。
   見つからない場合は、**その分類の履歴登録だけ**をスキップしてその旨を報告する
   (他の分類の処理・履歴登録は続行する)。
2. `mcp__task-manager__list_history(client_code="{関与先コード}")` を呼び、
   `content` が下表のその分類の値と一致するレコードが既にあるか確認する。
3. 見つかった場合: そのレコードの `historyId` を指定して
   `mcp__task-manager__update_history_entry` で更新する(重複登録せず、既存の1件を使い回す)。
4. 見つからない場合: `mcp__task-manager__create_history_entry` で新規に1件追加する。

分類ごとの `content`(固定値。かつ既存レコードとの照合キーを兼ねるため変更しないこと):

| 分類 | content |
| --- | --- |
| 支払 | `支払資料の自動分類、リネーム保存` |
| 売上 | `売上資料の自動分類、保存` |
| 給与 | `給与資料の自動分類、保存` |
| 銀行通帳 | `銀行通帳資料の自動分類、保存` |

`content`以外に設定する値は、いずれの分類・場合も以下で固定:

- 日付(date): 実行日(本日の日付、`YYYY-MM-DD`)
- 分類(category): その分類名自体(`支払`/`売上`/`給与`/`銀行通帳`)
- タスク名(series_code): 1.で控えた「資料受領」のseriesCode(分類ごとに個別に取得した値)
- 担当者(assignee): `整理係`
- ステータス(status): `完了`
- 内容(content): 上表の対応する値

**対象月(frame_codes)の反映**

対象月は固定値ではなく、その分類で今回処理したファイルの対象月に応じて、分類ごとに
都度セットする。

1. 対象月の算出元は分類によって異なる。
   - **支払**: Step 3で読み取った日付(西暦)から算出した対象月(`YYYY年M月`)。
   - **売上・給与・銀行通帳**: Step 3で読み取った`target_months`(ファイルごとの対象月
     リスト)を、その分類で今回処理した全ファイル分について集約(和集合・重複除去)
     したもの。
   その分類で今回処理したファイルが複数月にまたがる場合は、その全ての月を対象とする。
2. 算出した対象月(`YYYY年M月`)を、`mcp__task-manager__list_frames` の `frameCode`
   (`YYYYMM`形式。例: `2026年6月` → `202606`)に変換する。
3. 新規作成の場合: 変換した対象月のフレームコード一覧をそのまま `frame_codes` に設定する。
4. 更新の場合: 見つけた既存レコードが持つ対象月の一覧(`frameCodes`)を確認し、今回の対象月の
   うち既存の範囲に含まれていないものがあれば、既存の一覧にその不足分を追加した一覧を
   `frame_codes` に渡す(`update_history_entry` は指定したフィールドを丸ごと置き換えるため、
   既存分を含めずに渡すと過去の対象月が消えてしまう点に注意)。今回の対象月が既にすべて
   既存の範囲に含まれている場合は、`frame_codes` を指定しない(変更しない)。
5. その分類で対象月が1つも判定できなかった場合(売上・給与・銀行通帳で日付が全く
   読み取れなかった場合など)は、`frame_codes` を指定せずに履歴行だけ作成/更新し、
   その旨をユーザーに報告する。

複数の関与先をまとめて処理した場合は、関与先ごとにこの履歴更新(最大4分類分)も
繰り返す。

## 補足

- `filelist.xlsx` のヘッダーは: No., 受領ファイル名(サブフォルダ込みの相対パス、例 `旧/xxx.jpg`),
  受領ファイル作成日(受領ファイルのDrive上の更新日、JST), サイズ(MB), 種類,
  整理済ファイル名(サブフォルダ込み), 整理済ファイル作成日(処理実行日時), 分類,
  日付, 金額, 取引先, 内容, 区分, 支払方法, 消費税額, 仕訳No, 勘定科目名, remarks(備考。「のコピー」削除・同名スキップなど)。
  旧フォーマット(「ファイル名」「撮影日時」列、整理済列なし)は`append_filelist.py`が
  自動でリネーム・列挿入する(既存行の整理済列は空欄)。「分類」列に
  `支払`/`売上`/`給与`/`銀行通帳`のいずれかが入る(旧フォーマットのファイルには
  `append_filelist.py`が自動で列を追加する。既存の行の「分類」は空欄のままになるので、
  必要なら過去分は`支払`として扱ってよい)。
- 受領フォルダ配下のファイルは、分類の別なく処理後も削除・移動しない(整理済フォルダへ
  コピーした後も元ファイルは受領フォルダに残る)。次回実行時の「処理済みかどうか」の判定は、
  すべて`filelist.xlsx`の「受領ファイル名」列への記載の有無だけで行う。受領フォルダの
  元ファイルが残り続けるため、Drive上のファイル数だけで新規/既処理を判断しないこと。
- Google Driveのファイル作成APIは中身の上書き更新をサポートしないため、
  「新規作成 → 旧ファイルをtrash」で更新を表現する。これによりファイルIDは
  毎回変わるので、`drive_sync_upload.py`内でもIDをキャッシュせず、都度
  同名ファイルを検索し直してから置き換える(`drive_sync_common.py`の
  `find_file_by_name`/`upload_file_replacing`参照)。
- ファイルの「trash」は完全削除ではなくゴミ箱への移動(復元可能)。誤操作時の被害を
  抑えるため常にこちらを使い、完全削除にあたる操作は行わない。受領フォルダの元
  ファイルに対してはこのスキルはtrashを一切使わない(常に残す)。trashを使うのは
  `filelist.xlsx`・整理済フォルダ内ファイルの「旧バージョンの置き換え」時のみ
  (`drive_sync_upload.py`が担当)。
- 1領収書 = 1行が基本。1枚の領収書に複数の取引が混在する場合のみ複数行に分けてよい。
- 関与先ごとに `filelist.xlsx` も `整理済`
  フォルダも完全に独立している(他の関与先のデータと混ざることはない)。Step 0で
  対象が複数になった場合は、関与先ごとに Step 1〜7 を繰り返す。
- 売上・給与・銀行通帳に分類したファイルは `filelist.xlsx` に記録されるが、
  金額・取引先など支払のような内容は読み取らないため空欄のまま。日付だけはStep 3で
  対象月(`target_months`)判定のために全行読み取るが、複数月にまたがる場合1セルに
  収まらないため`filelist.xlsx`の「日付」列には反映せず、履歴(TaskHistory)の
  `frame_codes`反映にのみ使う。内容の集計や仕訳化が必要な場合は別途対応すること
  (このスキルはDrive上での分類・複製保存とファイル一覧・履歴対象月への記録までが役割で、
  それら以上のデータ加工は行わない)。
- Google Driveへのアクセス(MCPツール経由・`drive_sync_download.py`/
  `drive_sync_upload.py`経由のいずれも)は、AWS Secrets Manager に保存した実ユーザーの
  Google OAuthリフレッシュトークン(環境変数 `GOOGLE_USER_TOKEN_SECRET_NAME` で指定、
  デフォルト `task-agent/google-drive-user-token`)から都度取得される
  (`task_agent.py`の`_get_drive_service()`、および`scripts/drive_sync_common.py`の
  `_get_credentials()`/`get_drive_service()`参照。両者は同じSecrets Managerの
  シークレットを参照する)。ローカル版のようなtoken.jsonファイルへの依存は無い。
  当初はAgentCore Identityの3LO(ユーザー委任)OAuthフローやサービスアカウント方式も
  検討したが、前者は既知の未解決バグ(awslabs/agentcore-samples#801、コールバックが
  authorizationCode/stateを受け取れない)、後者はストレージクォータが無くアップロードに
  失敗するため、現在の方式に落ち着いている。

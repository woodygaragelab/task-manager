## 1. システム概要

- **用途**: 社内のタックス事務所（BPO: Business Process Outsourcing業務）向けのタスク管理ツール。
- **利用者**: 社内スタッフ数名（Web UI経由）、および担当者本人（Claude Desktop / claude.ai経由の自然言語操作）。
- **中核ドメイン概念**: 「クライアント（Client）」に対して、「シリーズ（Series、業務の種類）× フレーム（Frame、対象月）」の組み合わせで最小単位の「タスク（Task）」を管理する。例:「クライアントAの資料受領・2026年6月分」。加えて、クライアントごとの時系列の「履歴（History）」記録と、Google Driveフォルダを対象に外部AIエージェント（Bedrock AgentCore）を呼び出す「エージェント」機能を持つ。
- **最大の特徴**: **Web UIとClaude(MCP)という2つの利用インターフェースが、同一のDynamoDBデータソースを共有するデュアルインターフェース構成**。Web UIで更新した内容はClaude経由でも即座に参照でき、逆にClaude経由で作成・更新したタスクもWeb UI上でポーリング経由（4秒間隔）で確認できる。

## 4. ドメインモデル

### 4-1. 中核エンティティ

| エンティティ | 属性 | 説明 |
|---|---|---|
| **Client**（クライアント） | `clientCode`, `clientName`, `receiptFolderId`（任意）, `renamedFolderId`（任意） | 担当先。`receiptFolderId`/`renamedFolderId`はGoogle DriveフォルダID（4-4節参照） |
| **Series**（シリーズ、UI表示名「タスク」） | `seriesCode`, `seriesName`, `taskGroup`（表示名「分類」） | 業務の種類。例:「資料受領」「資料整理」「データ入力」。クライアント横断の共通マスタ。`taskGroup`は進捗表・タスク表の左端の分類列に使う自由記述の集約キー |
| **Frame**（フレーム、UI表示名「月」） | `frameCode`（`YYYYMM`形式、例`202606`）, `frameName` | タスクの対象タイムフレーム。例:「2026年6月」。年ごとに別レコード |
| **Task**（タスク） | `clientCode`+`seriesCode`+`frameCode`（複合キー）, `status`, `assignee`, `completeDate` | 最小単位の作業。あるクライアントの、あるシリーズの、あるフレーム分の進捗を1レコードで表す |
| **History**（履歴） | `clientCode`+`historyId`（UUID）, `date`, `category`, `assignee`, `status`, `content` | クライアントごとの時系列の作業記録。Task（Series×Frameの定型業務）とは独立した自由記述のログ。4-5節参照 |
| **AgentJob**（エージェントジョブ） | `clientCode`+`jobId`（UUID）, `agentId`, `status`, `prompt`, `result`/`error`, `ttl` | 「エージェント」タブから発行する非同期処理の実行記録。4-4節参照 |

**Client × Series × Frame の関係**（変更なし）:
- Series・Frameはクライアント横断の共通マスタ（クライアントごとの個別定義はしない）。
- Taskが`clientCode+seriesCode+frameCode`を持つことで「どのクライアントの・どの業務の・どの月分か」を一意に表す。
- Series・Frameは**事前登録不要**。タスク作成時に未登録のコードを指定すると自動的にマスタへ追加される（「使ったら生成される」設計）。加えて2026-07-28以降、ハンバーガーメニュー配下の一覧画面（`ClientListPage`/`SeriesListPage`/`FrameListPage`）から明示的な新規登録・削除も可能になった（4-3節参照）。
- Clientのみ、タスク作成に先立ちドロップダウンからの明示的な新規登録操作（`create_client`/`POST /clients`）を持つ。理由は9-2参照。

### 4-2. ステータス

```
未着手 → 依頼中 → 確認中 → 進行中 → 完了 / NA
```
2026-07-28（`ac56b95`）に3段階から**6段階**へ拡張された: `未着手` / `依頼中` / `確認中` / `進行中` / `完了` / `NA`。ドロップダウンで任意の値へ自由に行き来できる（一方向固定ではない）。UI上は「印影（はんこ）」風の`.stamp`クラスで、各段階に個別の配色（`frontend/src/App.css`）を割り当てている。`完了`のみ他の5段階と異なり傾き（`rotate`）を付けず、まっすぐ押されたスタンプとして視覚的に区別している。`completeDate`は`status`とは独立した手動入力項目（変更なし）。

### 4-3. マスタの編集可能化（2026-07-28）

`d92c1cf`（ハンバーガーメニュー追加）と`6409d93`（編集可能化）により、Client/Series/Frameの3マスタはいずれもWeb UI上の専用一覧画面から新規作成・削除ができるようになった。従来「タスク作成フローの中でのみ選択される付随的な存在」だったSeries/Frameも、この変更以降は独立した管理画面を持つ（ただし「タスク作成時に未登録なら自動登録」という4-1のフォールバック挙動自体は残っている）。

- `create_series`/`delete_series`、`create_frame`/`delete_frame`という明示的なCRUD関数が`task_repository.py`に追加された。これらは`create_task`内部の`_ensure_series_exists`/`_ensure_frame_exists`（冪等・サイレント登録）とは別物で、既存コードを指定すると`SeriesAlreadyExistsError`/`FrameAlreadyExistsError`を送出する（9-2節の非対称設計は維持しつつ、Series/Frame側にも明示的な登録手段が追加された形）。
- `update_client`/`delete_client`も同時に追加され、Clientマスタも一覧画面から編集・削除できる。

### 4-4. エージェント機能（2026-08-01、`6e90624`〜`d47a54b`）

Web UIの「エージェント」タブから、Amazon Bedrock AgentCore上で動く外部のAIエージェントを呼び出せる機能。API Gatewayの30秒制限を超える処理時間を扱うため、専用の非同期ジョブディスパッチLambda（`TaskAgentJobProcessorFunction`）を新設した。

**エージェントカタログ**: `frontend/src/AgentsPanel.jsx`に5種類のエージェントがハードコードされているが、現時点で実装（`LIVE_AGENT_IDS`）されているのは`archivist`（分類）の1つのみ。残り4種（`scout`＝受領/情報収集、`courier`＝会計/外部連携、`auditor`＝チェック/検証、`pinger`＝疎通確認/監視）はUI上のプレースホルダで、「開始する」ボタンは無効化されている。

**`archivist`（分類）エージェントの役割**: クライアントのGoogle Drive上の`receiptFolderId`フォルダにある未整理の領収書画像を、勘定科目ごとにリネーム・分類する。出力は`renamedFolderId`フォルダを想定。

**ジョブのライフサイクルとアーキテクチャ**:
1. ユーザーが「エージェント」タブでエージェントを選択し「開始する」を押すと、フロントエンドは`POST /clients/{clientCode}/agent-jobs`（body: `agentId`, `prompt`）を呼ぶ。`prompt`は`buildArchivistPrompt(client)`が組み立てる文字列で、`client.receiptFolderId`が設定されていれば対象フォルダのDrive URLをプロンプト本文に埋め込む（`d47a54b`で、表示中の指示内容と実際に送信されるプロンプトが食い違っていた不具合を修正し、両者を同一のヘルパー関数に統一した）。
2. `TaskApiFunction`（`api_src/app.py`）はこのリクエストを受けると、`task_repository.create_agent_job()`で`TaskAgentJobs`テーブルに`status="processing"`のジョブレコードを同期的に作成し、202を返すと同時に`TaskAgentJobProcessorFunction`を`InvocationType="Event"`（非同期・fire-and-forget）で起動する。API Gatewayの背後にいないこの後続Lambdaは`Timeout: 900`秒まで許容できる。
3. `TaskAgentJobProcessorFunction`（`agent_job_src/app.py`）は起動されると、まず`claim_agent_job()`で`ConditionExpression="attribute_not_exists(claimedAt)"`による条件付き更新を試みる。これは**Lambdaの非同期呼び出しがエラー・タイムアウト時に既定で自動リトライする**ため、対策なしでは同一ジョブに対してBedrock AgentCore呼び出し（および実際のDrive操作という副作用）が重複してしまうことへの防御。claimに失敗（＝既に処理済み/処理中）した場合は即座にreturnする。
4. claimに成功したら`boto3.client("bedrock-agentcore").invoke_agent_runtime()`を呼ぶ。`runtimeSessionId`にはジョブIDをそのまま使い、DynamoDB側のジョブレコードとAgentCore側のセッションを1:1に対応付けている。タイムアウトは`connect_timeout=10, read_timeout=850, retries={"max_attempts": 1}`という値を明示的に設定している。理由は、botocoreの既定`read_timeout`(60秒)は実際のAgentCore実行時間より短く、これを超えるとサーバー側はまだ実行中にもかかわらずboto3がクライアント側のソケットタイムアウトを起点に同一`runtimeSessionId`へ再送してしまい、Drive側の二重処理につながりかねないため。
5. 実行結果（またはエラー）を`complete_agent_job()`/`fail_agent_job()`で`TaskAgentJobs`に書き戻す（ステータスは`completed`/`error`）。`TaskAgentJobProcessorFunction`自身は`Tasks`/`TaskHistory`テーブルには一切書き込まない — Drive上のファイル操作を含む実際の副作用はすべてBedrock AgentCore Runtime側（このリポジトリの外）で完結する。
6. フロントエンド（`AgentsPanel.jsx`）は`GET /clients/{clientCode}/agent-jobs/{jobId}`を3秒間隔・最大100回（約5分）ポーリングし、`status`が`processing`でなくなった時点で`completed`→`done`/それ以外→`error`としてチケットのUIを更新する。タイムアウト・ポーリング自体のエラーもUI上で`error`表示する。チケットの表示状態は`useState`のみで保持する純粋なクライアント側状態であり、ページを再読み込みすると失われる（ただし裏側の`TaskAgentJobs`レコード自体はTTLの1日間は残る）。
7. `TaskAgentJobs`テーブルは`TimeToLiveSpecification`（属性`ttl`、`AGENT_JOB_TTL_SECONDS = 60*60*24`＝1日）でDynamoDB側から自動削除される。

**IAM上の注意点（`d47a54b`で修正済み）**: `bedrock-agentcore:InvokeAgentRuntime`の実際の認可チェックはベースのランタイムARNではなく`.../runtime-endpoint/*`配下のARNに対して行われる。当初ベースARNのみを許可していたため`AccessDeniedException`が発生し、`template.yaml`のIAMポリシーに`${AgentRuntimeArn}/runtime-endpoint/*`を追加して解消した。

**MCPサーバー（Claude側）からはエージェント機能は一切利用できない**（`create_agent_job`等はMCPツールとして登録されていない）。あくまでWeb UI専用の機能。

### 4-5. 履歴機能（2026-07-30〜31、`32dfa94`/`745c0d4`）

TaskとSeries×Frameの定型業務進捗とは別に、クライアントごとの自由記述の時系列ログを残す機能。`date`（日付）・`category`（分類、自由記述）・`assignee`（担当者）・`status`（ステータス、自由記述文字列でTaskの6段階ステータスとは無関係）・`content`（内容）の5項目を持つ。1クライアントに対して同一日付でも複数エントリを許容し、一覧は「分類昇順、同一分類内は日付昇順」でソートして返す（`list_history`内でクライアント側ソート、GSIは使わない）。

Web UI上ではインライン編集可能なテーブルとして表示され、行末に削除ボタンを持つ。加えて`390a3ea`でCSVアップロード機能を追加した: 外部ライブラリを使わない自前のCSVパーサ（`HistoryPanel.jsx`内、引用符エスケープ・改行コード両対応）でファイルをパースし、**行ごとに`POST /clients/{clientCode}/history`を逐次呼び出す**（バッチAPIは存在しない）。CSVの各セルは半角スペースで連結して`content`にそのまま格納され、`date`/`category`/`assignee`/`status`は空のまま登録される — 取り込み後に手動で分類・日付等を埋める運用を前提とした設計。

MCPツールとしては`list_history`/`create_history_entry`/`update_history_entry`の3つのみが公開されており（`5c9803f`）、`delete_history_entry`はMCP経由では呼べない。

### 4-6. 用語の変遷

初回コミット時点では「顧客」を表す`customerName`というキーが使われていたが、`clientCode`/`clientName`への改名を経て、最終的に「案件（Case）」という中間概念を廃し「クライアント（Client）」に一本化した（詳細経緯は旧設計書参照、13章）。

UI表示名と内部コード名が一致しない属性がある点に注意: `Series`はUI上「タスク」、`Frame`はUI上「月」、`taskGroup`はUI上「分類」と表示される（`7d352b2`/`ddb114f`/`b0a9b9c`等の一連のUI文言変更コミットによる）。API・DynamoDB上のフィールド名（`seriesCode`/`frameCode`/`taskGroup`）は変更していない。

`skill/bpo-task-manager/SKILL.md`という命名から、"BPO"（業務委託代行）＝税理士事務所などの外部委託業務向けであることが裏付けられる。

## 5. データモデル設計（DynamoDB）

DynamoDB（NoSQL、ORM・マイグレーション不使用、`boto3.resource("dynamodb")`を直接操作）。`tables.yaml`でLambdaスタック（`taskmanager`）とは別のCloudFormationスタック（`task-tables`）として管理。**6テーブル構成**（旧4テーブルに`TaskHistory`/`TaskAgentJobs`を追加）、いずれも`BillingMode: PAY_PER_REQUEST`、**GSIは1つも持たない**。

### 5-1. Tasks テーブル

```
PK: clientCode (String)
SK: taskKey (String, "{seriesCode}#{frameCode}" の連結文字列, 例 "SR001#202606")
属性: seriesCode, frameCode, status, assignee, completeDate, createdAt, updatedAt
```
`Query(PK=clientCode)`でクライアント別タスク一覧を取得。SKを`{seriesCode}#{frameCode}`の連結文字列にすることで、追加のインデックスなしに「シリーズ内でフレーム順」の並びが手に入る（`frameCode`が`YYYYMM`形式のため同一シリーズ内は時系列順）。単一タスクの取得・更新は`GetItem`/`UpdateItem(PK=clientCode, SK=taskKey)`で完結。「あるフレーム・あるシリーズを全クライアント横断で一覧する」というクエリは不要と判断したため、GSIは持たない。

### 5-2. TaskClients テーブル（クライアントマスタ）

```
PK: lookupBucket (String, 固定値 "CLIENT")
SK: clientCode (String)
属性: clientName, receiptFolderId(任意), renamedFolderId(任意)
```
`Query(PK="CLIENT")`で登録済み全クライアントを一覧取得できる（クライアント選択ドロップダウン用）。`receiptFolderId`/`renamedFolderId`は4-4節のエージェント機能用のGoogle DriveフォルダID（未設定時は属性自体を書き込まない）。

### 5-3. TaskSeries テーブル（シリーズマスタ、UI表示名「タスク」）

```
PK: lookupBucket (String, 固定値 "SERIES")
SK: seriesCode (String)
属性: seriesName, taskGroup(表示名「分類」)
```
`Query(PK="SERIES")`で登録済み全シリーズを一覧取得（タスク作成時のドロップダウン用）。`taskGroup`は`ddb114f`（2026-07-28）で追加。

### 5-4. TaskFrames テーブル（フレームマスタ、UI表示名「月」）

```
PK: lookupBucket (String, 固定値 "FRAME")
SK: frameCode (String, 例 "202606")
属性: frameName
```
`Query(PK="FRAME")`で登録済み全フレームを一覧取得。`frameCode`を`YYYYMM`のゼロ埋め文字列にしているため、文字列ソートがそのまま時系列順になる。

### 5-5. TaskHistory テーブル（履歴、新設）

```
PK: clientCode (String)
SK: historyId (String, UUID)
属性: date, category, assignee, status, content, createdAt, updatedAt
```
`Query(PK=clientCode)`でクライアントの全履歴を取得し、`list_history()`内でクライアント側（Lambda側）ソート（分類→日付→作成日時の順）する。GSIなし。TTL設定なし（永続保持）。

### 5-6. TaskAgentJobs テーブル（エージェントジョブ、新設）

```
PK: clientCode (String)
SK: jobId (String, UUID)
属性: agentId, status(processing/completed/error), prompt, result または error, claimedAt, createdAt, updatedAt, ttl
```
`TimeToLiveSpecification`（属性`ttl`、`Enabled: true`）により、`AGENT_JOB_TTL_SECONDS`（1日）経過後にDynamoDB側が自動削除する。GSIなし。`claimedAt`は4-4節の二重実行防止用。

### 5-7. マスタ自動登録の一貫性

Series/Frameは、`ConditionExpression: attribute_not_exists(...)`付き`PutItem`で冪等に登録し、`ConditionalCheckFailedException`（＝既存）は正常系として握りつぶすパターンを共通で使用（`_ensure_series_exists()` / `_ensure_frame_exists()`）。これはタスク作成時の自動登録専用の内部ヘルパーであり、4-3節で追加された明示的な`create_series()`/`create_frame()`（既存コード指定時は`SeriesAlreadyExistsError`/`FrameAlreadyExistsError`を送出）とは別物として使い分けられている。Clientは元からこのサイレント登録パターンを使わず、`create_client()`で明示的にエラーを返す（9-2参照）。

### 8-1. Web UI向け（Cognito）

Cognitoは使わず、`AccessControlMiddleware`による固定Bearerトークンまたは Anthropic公開IPレンジでの認可。トークンは`NoEcho: true`のSAMパラメータとして管理。

### 8-4. 既知のセキュリティ課題

## 9. 再設計における主要な意思決定

旧設計書（2026-07-27時点）で確定した意思決定に加え、履歴・エージェント機能の追加時に確定した判断を記す。

### 9-1〜9-6（旧設計書からの継続、要約）
- 9-1: 「案件（Case）」を廃し「クライアント（Client）」に統一。
- 9-2: Clientのみ`create_client`という明示的な登録手段を持つ（Series/Frameはタスク作成時の自動登録が基本だが、4-3節の通り2026-07-28以降は両者とも明示的なCRUD画面を追加で持つようになった。ただし「タスク作成時の自動登録」という非対称の原則自体は維持）。
- 9-3: タスクをClient×Series×Frameに分解。
- 9-4: `frameCode`を`YYYYMM`形式にした理由（文字列ソート＝時系列順）。
- 9-5: GSIを持たない設計（6テーブルに増えた現在も踏襲。TaskHistory/TaskAgentJobsもクライアント単位のクエリのみで足りるためGSIなし）。
- 9-6: 既存データを移行しなかった理由。

（各項目の詳しい経緯は本書の初版、Gitログの`d5c7c24`時点の`docs/設計書.md`を参照。データモデル自体は変わっていないため要点のみ再掲した。）

### 9-7. エージェント処理を「同期API＋非同期Lambda」の2段構成に分離した理由
API Gateway HTTP APIの統合タイムアウトは30秒が上限だが、Bedrock AgentCoreの実行（Google Driveのファイル走査・リネーム）は数十秒〜数分かかる。API Gatewayの背後にいる`TaskApiFunction`はジョブレコードの作成のみを同期的に行い、実際の長時間処理はAPI Gatewayを経由しない別Lambda（`TaskAgentJobProcessorFunction`、Timeout 900秒）にLambdaの`Event`非同期invocationで委譲する構成にした。フロントエンドはジョブIDをキーにポーリングして結果を取得する。

### 9-8. エージェントジョブに「claim」ステップを設けた理由
Lambdaの非同期(`Event`)呼び出しは、呼び出し先が例外を投げたりタイムアウトしたりすると既定で自動的に再試行する。何も対策をしないと、Bedrock AgentCore呼び出し（＝Google Drive上のファイルリネームという冪等でない副作用）が同一ジョブに対して複数回実行されるおそれがある。`claimed_at`属性への条件付き書き込み（`attribute_not_exists`）を「一度だけ勝てる」ゲートとして使うことで、この二重実行を防いだ。

### 9-9. エージェントジョブに1日のTTLを設定した理由
ジョブレコードは実行結果のポーリング用に一時的に必要なだけで、恒久的な監査ログとしての価値は低いと判断し、DynamoDBのTTL機能で1日後に自動削除する設計にした（対照的に、履歴（History）テーブルは業務ログとして永続保持し、TTLを設定していない）。

### 9-10. CSVアップロードを「行ごとに既存APIを叩く」実装にとどめた理由
バッチ専用のAPIエンドポイントを新設せず、フロントエンドで自前のCSVパーサを実装し、既存の`POST /clients/{clientCode}/history`を行数分繰り返し呼び出す実装にした。CSVの列と履歴エントリの項目（日付/分類/担当者/ステータス/内容）を1:1にマッピングする仕様が固まっていなかったため、まずは「各行をまるごと`content`に詰めて取り込み、後から手動で分類・日付を埋める」という最小実装で運用を開始し、列マッピングの精緻化は今後の課題とした（12章参照）。

### 9-11. Series/Frameマスタを後から編集可能にした理由
初期実装では「タスク作成時に未登録なら自動登録」のみでSeries/Frameを管理していたが、誤って登録してしまったコードの削除や、タスク作成前に事前にマスタを整備したいという運用上のニーズから、ハンバーガーメニュー配下に独立したCRUD画面（`SeriesListPage`/`FrameListPage`）を追加した。自動登録のフォールバック自体は運用の手間を減らすため残している。

### 10-2. 再デプロイ時に発生したトラブルと対応（このマシン固有・恒久的な注記、2026-07-27時点、変更なし）

| 問題 | 原因 | 対応 |
|---|---|---|
| `task-tables`スタックが`UPDATE_ROLLBACK_COMPLETE`のまま実テーブルが消失していた | DynamoDBのキースキーマ変更はインプレース更新できず、ロールバック後にスタック状態と実リソースがズレる「ドリフト」が発生 | `task-tables`スタックを削除し、新`tables.yaml`で`CREATE_COMPLETE`として作り直した |
| AWS CLIが`SSL: CERTIFICATE_VERIFY_FAILED`で失敗 | このマシンではNorton Antivirusが常駐しHTTPS通信をSSL検査(MITM)しており、AWS CLI(Python/botocore)がそのルート証明書を信頼していない | `AWS_CA_BUNDLE`環境変数にNortonの証明書を指定 |
| `aws cloudformation deploy`実行時に`cp932`デコードエラー | `tables.yaml`のコメントに残っていた日本語文字がこのマシンのロケール(cp932)でデコードできなかった | コメントを英語に修正 |
| `sam build`（コンテナなし）が`pywin32`の解決に失敗 | `mcp`パッケージが`sys_platform == "win32"`条件で`pywin32`に依存しており、Windows上でのネイティブビルドがLambdaのLinuxターゲットと噛み合わず失敗 | `sam build --use-container`でLinuxコンテナ内ビルドに切り替え |
| コンテナ内`pip`が`SSL: CERTIFICATE_VERIFY_FAILED`でPyPIに到達できない | コンテナ内のpipもNortonのMITM証明書を信頼していない | `--container-env-var-file`で`PIP_TRUSTED_HOST`を注入 |

これらは全てこの開発マシン固有の環境要因であり、リポジトリのコード自体に問題があったわけではない。

### 10-3. スタック名移行とデプロイ実績

1. `template.yaml`の物理リソース名を`task-mcp-server`/`task-api`/`task-agent-job-processor`/`task-manager-users`/`task-manager-webapp`から`taskmanager-mcp`/`taskmanager-api`/`taskmanager-agent-job-processor`/`taskmanager-users`/`taskmanager-webapp`へ変更。
